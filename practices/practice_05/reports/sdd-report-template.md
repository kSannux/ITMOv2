# ДЗ 5: две команды — одна фича — отчёт

Фича: `export-filtered-json` — экспорт текущей страницы таблицы в JSON.
Отчёт составлен по истории работы в этом чате, включая предоставленный
пользователем ранний фрагмент с ревью Spec Reviewer, и созданным артефактам.
OpenSpec сравнивается по [учебной презентации, стр. 16](../prenetation.pdf),
а не по выполненному в этом проекте OpenSpec-циклу.

## 1. Две спецификации и согласование

Две спецификации были созданы **в отдельных чатах**, что пользователь
подтвердил в этой переписке. Так эмулировались две команды: первая описала
UI — действия, состояния и ошибки; вторая — данные, алгоритм и Python API.
Затем результаты объединены в общем контракте и переданы отдельному
Spec Reviewer для поиска противоречий. Ссылки/экспорты исходных чатов
в комплект отчёта не приложены; факт их раздельного ведения подтверждён автором.

| Артефакт | До финальной синхронизации | После синхронизации |
| --- | --- | --- |
| UI | [исходная версия](../specs/01-export-json/before-alignment/ui-spec.md) | [актуальная](../specs/01-export-json/ui-spec.md) |
| Логика | [исходная версия](../specs/01-export-json/before-alignment/logic-spec.md) | [актуальная](../specs/01-export-json/logic-spec.md) |

Общий контракт: [spec.md](../specs/01-export-json/spec.md).
Подробный API: [python-export.md](../specs/01-export-json/contracts/python-export.md).

### Принятые решения

Основные решения по данным и UX явно приняты пользователем после ревью
и закреплены в общем контракте. Детали Python API уточнены при планировании,
а Flask-интерфейс добавлен по последующему запросу пользователя.

| Вопрос | Принятое решение | Основание и смысл |
| --- | --- | --- |
| JSON-массив или объект | Объект: export_date, total_items, filters_applied, data | Общий контракт; позволяет хранить данные вместе с контекстом выгрузки |
| Все страницы или текущая | Только текущая страница, порядок строк сохранён | Общий контракт; выгрузка соответствует просматриваемому срезу |
| Скрытые столбцы / порядок ключей | Только видимые поля; порядок ключей незначим | Общий контракт; скрытые поля не попадают в файл |
| Пустой результат | Native disabled + tooltip на фокусируемой обёртке, без тоста | Общий контракт; устраняет противоречие клика по disabled-кнопке, сохраняет доступность |
| Фильтры и сортировка | Копия dict; сортировка отражена порядком строк, не metadata | Общий контракт; входные фильтры не изменяются |
| Неподдерживаемые значения | Явная нормализация; без fallback str/asdict | Python-контракт; ошибки не скрываются за произвольной строкой |
| NaN/Infinity | Строки в data; нефинитные float в фильтрах запрещены | Общий и Python-контракты; строгий JSON без изменения содержимого фильтров |
| Время и имя | UTC-Z; export-YYYYMMDD-HHMMSS.json | Общий контракт; независимость от локального часового пояса |
| Смена фильтра при запросе | Файл по снимку начала; кнопка затем по актуальной странице | Контракт UI и реализация; изменения таблицы не меняют уже начатую выгрузку |
| Реализация логики | Python stdlib и pytest | Требование пользователя из предыдущего этапа, отражённое в плане и задачах |
| Расположение | Все актуальные файлы в practice_05 | Прямой запрос пользователя: перенести актуальные версии, при конфликтах выбрать актуальные |
| Интерфейс | Минимальный локальный Flask-сайт по спецификации | Прямой запрос пользователя после сравнения реализации с ДЗ |
| Документация | Обе спеки согласовать с контрактом, подготовить отчёты | Прямой запрос пользователя на завершающем этапе |

### Выводы из проделанной работы

- **Польза Spec Kit:** разделение spec → plan → tasks сделало API, исключения,
  нормализацию и проверку производительности явными до завершения библиотеки.
  Пример — отдельный Python-контракт и последовательность тестов/реализации.
- **Затраты:** два корня проекта привели к ошибкам запуска prerequisites,
  дублированию документов и последующему переносу. Исходные командные спеки
  отстали от общего контракта. Checklist задач описывал библиотеку, а не всё ДЗ.
- **Отличие OpenSpec по материалам курса:** sync/archive явно выделяют
  обновление актуальных требований и завершение изменения. Предположительно,
  такой шаг помог бы раньше заметить рассогласованные копии, но это не
  результат практического эксперимента с OpenSpec в данном проекте.
- **Рекомендация для следующего изменения:** сохранить единый корень и
  источник истины, проверять согласованность обеих спек перед кодом и
  включать UI/сквозные проверки в план сразу. Окончательное личное предпочтение
  между Spec Kit и OpenSpec пользователь в чате не высказывал.
