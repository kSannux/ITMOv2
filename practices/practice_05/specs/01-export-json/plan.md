# Implementation Plan: export-filtered-json

**Branch**: `01-export-json` | **Date**: 2026-10-29 | **Spec**: [spec.md](spec.md)

**Input**: `practices/practice_05/specs/01-export-json/spec.md`, согласованные решения пользователя и уточнённая [спецификация в корне репозитория](../../../../specs/01-export-json/spec.md).

## Summary

Спроектировать Python-библиотеку экспорта уже подготовленных строк текущей страницы в JSON-объект с `export_date`, `total_items`, `filters_applied`, `data`. Использовать стандартную библиотеку во время выполнения и pytest для проверки. Экспорт сохраняет порядок строк, Unicode и значения JSON, нормализует явно поддержанные специальные типы, сообщает об ошибках исключениями.

В practice_05 находится ранняя копия spec.md. При расхождениях применяются последующие решения пользователя: только текущая страница, только видимые столбцы, порядок ключей незначим, сортировка отсутствует в метаданных, filters_applied — копия словаря, NaN/Infinity всегда строки в данных, нативный disabled с tooltip на фокусируемой обёртке, имя файла по UTC. Перед реализацией необходимо синхронизировать локальный spec.md с этими решениями; возврат к ранним требованиям о тосте при клике на disabled недопустим.

Python-результат — содержимое файла и вспомогательная функция имени. Выбор страницы/столбцов, скачивание, кнопка, tooltip и тосты принадлежат вызывающему UI; соответствующий контракт описан отдельно. Реального UI-приложения в practice_05 нет, поэтому pytest проверяет библиотеку и границу вызова, а визуальная приёмка остаётся задачей интеграции.

## Technical Context

**Language/Version**: Python 3.11+ (окружение репозитория также поддерживает 3.12).

**Primary Dependencies**: stdlib `json`, `datetime`, `copy`, `math`, `decimal`, `enum`, `base64`; внешних runtime-зависимостей для экспорта нет.

**Storage**: работа в памяти; запись и доставка файла выполняются вызывающей стороной.

**Testing**: pytest из существующего окружения `.venv`; контрактные и негативные тесты в `tests/test_export_json.py`, отдельный измерительный сценарий для SC-4.

**Target Platform**: Linux, переносимый Python-код без привязки к ОС.

**Project Type**: библиотека с публичными Python-функциями; HTTP/CLI не требуются.

**Performance Goals**: SC-4 — формирование до 10 000 строк за ≤2 с в 95% измерений; SC-1 — старт скачивания до 5 с для ≤5 000 строк, проверяется при UI-интеграции. Это разные измеряемые интервалы.

**Constraints**: строгий JSON; неизменность входов; `ValueError("Empty dataset")` для пустого списка; отсутствие молчаливого превращения неподдержанных объектов в строки; json null сохраняется как null. Фильтры принимаются в JSON-совместимой форме и копируются без нормализации.

**Scale/Scope**: одна страница за вызов; линейные время/память относительно размера сериализуемого дерева, без потоковой выдачи. Число строк не ограничивает размер отдельного значения, поэтому измерения используют фиксированную описанную нагрузку.

## Implementation sequence and validation

1. Синхронизировать спецификацию practice_05 с принятыми решениями и заполнить tasks.md по сценариям: базовый экспорт (P1), пустой набор (P1), ошибки (P1), длительная операция (P2). Приоритеты здесь — предложение планирования, исходные сценарии не имеют P-меток.
2. Дополнить pytest-проверки контракта до исправления модуля. Проверять точное сообщение пустого набора, null/bool, вложенные структуры и порядок, копию фильтров, Unicode, UTC, нормализацию, ошибочные типы, циклы и отсутствие мутаций при неудаче.
3. Исправить сериализатор и добавить функцию UTC-имени по [контракту](contracts/python-export.md). Существующий черновик превращает None в строку, модифицирует представление фильтров и теряет микросекунды datetime; это регрессии, подлежащие исправлению.
4. Выполнить [quickstart](quickstart.md), включая отдельную проверку производительности и штатный runner. Зафиксировать внешние ошибки сбора тестов отдельно от результатов тестов экспорта.
5. Выполнить UI-приёмку при подключении библиотеки к таблице; библиотечные тесты не подтверждают DOM-доступность или фактическое скачивание.
